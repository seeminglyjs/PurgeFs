# change-brief

한 세션에서 **켜면 그 작업이 끝날 때까지** 매 응답 맨 아래에 브리핑 블록을 붙인다.
끄는 말: "브리핑 꺼" / "change-brief off".

## 규칙

- **위치**: 항상 응답 **제일 하단**. 본문은 평소대로 쓰고, 마지막에 `---` 로 끊고 블록 하나만.
- **블록은 하나.** 중간중간 쪼개서 뿌리지 않는다.
- **없으면 비운다.** 해당 항목에 쓸 게 없으면 줄을 아예 뺀다. 채우려고 늘리지 않는다.
- 쉬운 말. 전문용어는 쉬운 말 뒤 소괄호로만. (CLAUDE.md 응답 규칙 그대로)
- 정직하게. 안 돌린 확인은 "미실행"이라 쓴다.
- **파일은 눌러서 열리게 쓴다.** 아래 "파일 표기" 규칙을 모든 항목(핵심 지점·핵심 코드·손댈 파일)에 똑같이 적용한다.

### 파일 표기 — 눌러서 열리는 링크로

- 형식: `[파일이름.확장자:줄번호](<작업폴더 기준 전체 경로:줄번호>)`
  - 예: `[SchedulerManualRunner.java:98](<ontology/src/main/java/com/elegant/ontology/domain/scheduler/service/SchedulerManualRunner.java:98>)`
- **경로를 `...` 로 줄이지 않는다.** 줄이면 링크가 안 열린다. 화면에 보이는 글자만 짧게(파일이름:줄) 하고, 링크 주소는 전체 경로를 쓴다.
- 경로 기준은 **작업 폴더(root-ontology)**. 하위 레포도 `ontology/…` · `ontology-front/…` 로 시작해 적는다.
- **주소는 항상 `<`  `>` 로 감싼다.** 경로에 괄호가 들어가는 폴더(`(base)` 등)가 있으면 안 감쌌을 때 링크가 깨진다.
- 줄 번호는 **실제 파일에서 확인한 값**만 쓴다. 어림짐작으로 적지 않는다(못 찾겠으면 줄 번호를 빼고 파일만 건다).

## 형식 — 착수 전 (파일 손대기 직전)

```
---
### 변경 브리핑 (착수 전)
**생기는 것** · <새 파일·함수·컬럼·API·화면>
**바뀌는 것** · <기존 동작이 어떻게 달라지나>
**손댈 파일** · [a.java](<path/a.java>) [b.tsx](<path/b.tsx>)
**안 건드림** · <오해 살 만한 인접 영역만. 없으면 줄 삭제>
**위험 한 줄** · <깨질 수 있는 지점 / 없으면 "없음">
```

한 항목은 한 줄. 두 줄 넘어가면 자른다.

## 형식 — 작업 후

```
---
### 변경 브리핑 (완료)
**한 줄 요약** · <이 변경으로 무엇이 달라졌나>
**흐름**
```
<요청 시작점부터 끝까지. 갈림길과 막히는 지점이 보이게. 아래 "흐름 그리는 법" 참고>
```
**핵심 지점**
- [file.java:120](<path/file.java:120>) — <이 블록이 하는 일 / 왜 이렇게>
- [file.tsx:44](<path/file.tsx:44>) — <…>
**핵심 코드**
[file.java:120](<path/file.java:120>) — <이 조각이 하는 일 한 줄>
```java
<실제 파일 내용 그대로. 판단이 일어나는 줄이 보이게 앞뒤 맥락 포함>
```
→ <왜 이렇게 했나 / 이게 없으면 뭐가 깨지나 한 줄>
**확인** · <실제 돌린 명령 + 결과 한 줄. 못 돌렸으면 "미실행 — <이유>">
```

- 핵심 지점은 **최대 4줄**. 바뀐 파일 전부 나열 금지, 중요한 것만.
- 확인은 프레임워크 새로 깔지 말고, 깨지면 티 나는 **가장 작은 것 하나**.

### 흐름 그리는 법 (코드보다 먼저 읽히는 그림)

- **글자 그림(ASCII)으로, 코드블록 안에.** 터미널은 mermaid 를 그림으로 안 그린다 — 글자 그림만 어디서나 보인다.
- **최대 14줄.** 넘으면 흐름이 아니라 설계도다. 이번 변경과 무관한 단계는 뺀다.
- 한 단계 = `[어디서] 무엇을` 한 줄. 파일명이 아니라 **동작**으로 쓴다.
- **갈림길과 막히는 지점을 반드시 표시한다.** 조건 → 통과/거절 두 갈래, 거절 사유는 실제 사용자에게 보이는 문구로.
- 서버가 여러 대·백그라운드 실행처럼 **동시에 도는 것**은 옆으로 갈라 그린다(순서대로 늘어놓으면 거짓말이 된다).
- 상태가 바뀌는 지점(락 잡음/풀림, 저장, 화면 갱신)은 `*` 로 표시하고 그림 아래 한 줄로 설명.
- 화면 변경만 있고 흐름이랄 게 없으면(문구 수정 등) **이 항목은 통째로 뺀다.** 억지로 그리지 않는다.

예:
```
[화면] 지금 실행 클릭
   └─ 부하 무거움? ── 예 ─→ 경고 확인창 ─ 취소 ─→ 끝
                      아니오/확인
                         ↓
[서버] POST /scheduler/{key}/run
   ├─ 꺼져 있음      ─→ 거절 "먼저 켠 뒤 실행하세요"
   ├─ 락 못 잡음     ─→ 거절 "이미 실행 중입니다"
   └─ 락 잡음 *        ─→ 즉시 응답 ─→ [화면] "실행 중" 표시
                              ↘ (딴 스레드) 작업 실행 → 락 풀림 *
```
`*` = DB 락 표(`shedlock`) 상태가 바뀌는 지점. 서버 여러 대가 이 표를 같이 본다.

### 핵심 코드 쓰는 법 (이 항목이 브리핑의 본체다)

- **조각 2~3개**, 조각당 **5~20줄**. 한두 줄만 잘라 붙이지 않는다 — 그 줄만 봐선 언제 도는 코드인지 알 수 없다.
- 조각마다 **세 가지를 붙인다**: ① 위치 `파일:줄`, ② 위 한 줄 = 하는 일, ③ 아래 한 줄 = 왜 이렇게 / 없으면 뭐가 깨지나.
- **실제 파일 내용 그대로** 붙인다. 브리핑용으로 다시 쓰거나 줄이지 않는다(줄 번호와 안 맞으면 확인이 안 된다).
- 고를 기준 = **판단·조건·순서가 들어간 곳**. 가져다 쓰기(import)·타입 선언·화면 꾸미기(CSS)는 안 넣는다.
- 고친 코드면 **바뀐 줄이 보이게** 자른다. 필요하면 `// 전:` 한 줄로 옛 동작을 같이 적는다.
- 흐름이 여러 파일을 건너뛰면(호출 → 처리 → 화면) **그 순서대로** 조각을 배치한다.

## 하지 말 것

- 비유·동화식 설명(우편함·상자 등) 금지. 실제 서비스 흐름으로 설명한다.
- 안 물어본 배경·대안 나열 금지.
- 이 블록을 본문에서 다시 요약하지 않는다. 중복이다.
